# Novice Guide to WebOS Mesh (Legacy App Integration)

Welcome to SPP! If you are completely new to this framework, you might be wondering: *"I have an old, massive WordPress (or Magento, or Drupal) site. How do I move it into the modern SPP WebOS without having to rewrite 10 years of messy PHP code?"*

The answer is the **SPP Mesh Router**. 

The Mesh Router is a brilliant layer in SPP that allows you to "mount" your old application directly into SPP. You don't have to rewrite a single line of your old code. SPP acts like an invisible wrapper around your legacy app.

## Foundational Concepts

### What is a "Passthrough Route"?
Normally, when you create an app in SPP, it uses MVC Controllers and strict Database Policies. 
But when you mount a **Legacy App** into the Mesh, SPP treats it as a "Passthrough Route". 

When a user visits `/blog` (your mounted WordPress site), SPP intercepts the request, looks at its configuration, and then simply *includes* your old WordPress `index.php` file. WordPress runs exactly as it did before, executing its own messy database queries perfectly.

### A La Carte Features (Partial Integration)
If SPP just passed the traffic through, it would be a bit useless. The magic of the Mesh Router is **Partial Integration**. 

You can inject SPP features into your old app seamlessly:
- **`sso_auth`**: SPP will start the session and log the user in *before* handing control to WordPress. WordPress instantly knows who is logged in!
- **`ui_mesh`**: SPP captures the HTML output of WordPress and glues the beautiful SPP Global Navigation Bar to the top of it.
- **`hardware_quota`**: SPP puts a strict RAM limit (e.g., 128MB) on WordPress, killing it instantly if a messy plugin tries to crash the server.
- **`security_headers`**: SPP automatically injects modern HTTP security (like X-Frame-Options against Clickjacking) into the legacy app's response.
- **`telemetry`**: SPP wraps the legacy app in W3C Trace Context distributed tracing, logging its performance directly into your enterprise dashboard.

## Lifecycle & Architecture

1. **The Request Arrives:** The user visits `/blog`.
2. **Route Priority:** SPP first checks if there is a modern `UserController` listening to `/blog`. If not, it falls back to the Mesh Router.
3. **YAML Evaluation:** The `MeshLoader` instantly reads `etc/mesh.yml` (compiled for 0ms overhead) and sees that `/blog` points to `/var/www/wordpress/index.php`.
4. **Execution Ejection & Scope Isolation:** Because legacy apps require the Absolute Global Scope to run without crashing, SPP dynamically throws a `MeshPassthroughException`. This elegantly stops SPP's internal execution stack and forces the process to bubble back up to the absolute root (`index.php`).
5. **CWD Pivoting & Variable Mocking:** At the global root, SPP intercepts the exception, pivots the Current Working Directory (`chdir()`) so the legacy app feels at home, and completely unregisters its own Error Catchers (so the legacy app can handle its own errors).
6. **Execution:** SPP natively `require`s the WordPress file at the Global Scope. The legacy app executes natively, completely unaware it is being shielded by the SPP hypervisor.

## Step-by-Step Tutorial

Let's mount a legacy application!

### Step 1: Place Your Legacy App
Make sure your old app (e.g. WordPress) is on the server. For this example, let's say it is located at `/var/www/wordpress/index.php`.

### Step 2: Use the CLI to Mount the App
Instead of writing confusing PHP code, we use the SPP Terminal. Run this command:

```bash
php spp.php mesh:add /blog /var/www/wordpress/index.php --integration=partial --features=sso_auth,ui_mesh,security_headers,telemetry
```

**What did this do?**
- It told SPP to listen to `/blog`.
- It told SPP to send traffic to `/var/www/wordpress/index.php`.
- It added SSO, a modern UI header, hardened HTTP headers, and enterprise tracing automatically!

### Step 3: Verify the YAML Configuration
Under the hood, SPP wrote this into `etc/mesh.yml`:
```yaml
mesh_routes:
  /blog:
    target: /var/www/wordpress/index.php
    integration: partial
    features:
      - sso_auth
      - ui_mesh
      - security_headers
      - telemetry
```

### Step 4: Visit Your App
Open your browser and visit `http://your-server.com/blog`. 
You will see your old WordPress site, but instantly, you'll notice the modern SPP Navigation Bar injected at the top, you will already be logged in thanks to SSO, and your network inspector will show highly secured, strict HTTP headers generated by SPP!

## Managing Your Mesh

If you ever want to see all your mounted legacy apps, just ask SPP:
```bash
php spp.php mesh:list
```

If you want to add a hardware RAM limit to the blog because a plugin is misbehaving:
```bash
php spp.php mesh:update /blog --add-feature=hardware_quota
```

If you want to delete the integration entirely:
```bash
php spp.php mesh:remove /blog
```

And that's it! You have successfully onboarded a brittle legacy application into an enterprise-grade WebOS without touching a single line of legacy code.
